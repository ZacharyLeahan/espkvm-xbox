# C790 PCM transport recovery, 2026-10-25

This follows C790-AUDIO-2026-10-25.md. The user confirmed its eight-second
capture matches Super Mario War and sounds clear. The Xbox testing chat
confirmed another KVM-only maintenance window; Xbox power, game session and
files were preserved throughout. Raw audio, packet headers, private build
configuration and logs stay in ignored observations/c790-transport-2026-10-25/.

## Reproduction and cause of premature disconnect

The installed DMA-reservation candidate failed independently with curl: only
1,475,584 response bytes arrived before EOF, about 7.7 seconds of PCM. There
were no video viewers. A second curl trial reached its intentional 30-second
limit with 5,605,440 bytes (29.195 seconds PCM), demonstrating intermittent
behavior rather than reliable recovery. Its receiver-side packet trace had
a 223.083 ms maximum audio arrival gap. A nearby cumulative ACK left the Mac
554 us after the preceding audio data. Neither result alone locates link loss.

The existing default-off HTTP TX diagnostics and ESP-Hosted packet counters
were enabled temporarily in the matching build.s3-player1 profile. The first
successful post-boot diagnostic trial failed early with these observations:

- The 250 ms application budget expired after a 259,644 us write, with only
  512/960 bytes accepted. The stream had sent 797,280 frames (16.61 seconds),
  1,440 confirmed delivered-index gap frames, zero capture epoch resets and
  12,240 subscriber queue-drop frames including disconnect cleanup.
- Firmware ACK-ingress and lwIP lastack agreed. No new PCM-flow ACK arrived
  for 294 ms. The send buffer was full at 8,192 queued bytes / nine unacked
  segments, no unsent segments, and an open 65,535-byte peer window. Socket
  calls were at most 635 us, yields at most 12,094 us, core-lock waits 2-3 us.
  Gross sender scheduling delay and receiver window exhaustion were not
  observed at this failure. Local TX drop/credit counters stayed zero; those
  counters do not establish successful radio or AP delivery.
- The simultaneous receiver header trace agreed with lastack and showed no
  arrival of the next queued 8 KB before the application's FIN. Those missing
  bytes began arriving 1.374 seconds after the last earlier PCM packet, and
  eventually completed before EOF. The application had already ended the
  stream. The trace had zero kernel capture drops. Host timestamps do not
  establish the packet's actual transmission time over the radio.

The concrete application failure is that a 250 ms write deadline closes an
otherwise recoverable TCP stream before retransmission completes. The lower
layer cause of the missing/delayed packets remains unidentified: these tests
cannot distinguish AP/radio/C6/SDIO behavior. They do not justify patching ACK
processing, flashing C6, or claiming link packet loss is fixed.

## Bounded recovery change

Commit 0c57c55 gives PCM writes a two-second budget. TCP and application queue
sizes, TCP_NODELAY, source format, capture scheduling and browser prebuffer
are unchanged. The subscriber continues retaining only about 40 ms of recent
capture during backpressure; its explicit drop and gap counters remain.
The browser already drops stale bursts and bounds its local playback queue.
A completed stalled write can contain old audio, so this is connection
resilience, not a guarantee of current-time output, lip sync or gap-free sound.
The observer's socket read timeout is three seconds so it outlasts the sender's
recovery budget. Other HTTP sessions retain their own deadlines, capped at
five seconds. The TCP probe recognizes the new PCM budget when enabled.

Host tests compile production TX loops with AddressSanitizer/UBSan and check
recovery beyond 250 ms, a two-second upper bound, short writes, interrupted
writes, fatal errors, independent session locking and descriptor reuse. These
passed, along with the three PCM evidence helper tests and git diff --check.

## Verified normal build and fully wired acceptance

The normal candidate was regenerated after committing 0c57c55 and identifies
as `v.0.56.1-167-g0c57c55-dirty`. The dirty suffix includes unrelated local
roadmap edits. Firmware SHA-256:
`ba872f5f596348ef95eb5a2e107f2461b73e3d66d73fd60cd8f2aeb2bf9e924d`.
The diagnostic strings and configuration flags are absent in this binary.
Its binary and ELF are preserved privately alongside the test artifacts.

OTA deployment did not reliably select the intended image. Opening the serial
monitor captured two boots of the older diagnostic image and an early startup

that restart failed to connect. This is separate from the measured audio
failure and is not claimed fixed here. A USB app-only flash installed the

and preserved NVS, partition table, storage and controller pairing:

```sh
. tools/env.sh
python3 -m esptool --chip esp32p4 -p /dev/cu.usbmodem1101 -b 460800 \
  --before default-reset --after hard-reset write-flash \
  --flash-mode dio --flash-freq 80m --flash-size 16MB \
  0x420000 build.s3-player1/espkvm.bin
```

HTTP system/info then confirmed the exact 0c57c55 version in ota_1. Runtime
logs no longer emit tx_probe entries. The first verified normal-build Wi-Fi
180-second request still FAILED: the write reached its two-second deadline,
sent 681,840 complete server blocks' frames, and the WAV preserved 681,968
frames including the final partial block's accepted bytes. The sender logged
67,680 delivered-index gap frames, 161,760 queue-drop frames including cleanup,
zero epochs, max successful send 1.347909 s and failed send 2.005450 s.
Therefore the recovery budget is a bounded resilience improvement, not a
wireless fix or a guarantee of connection continuity on a lossy link.

The user then connected the Mac to the same wired network. Its USB LAN adapter
appeared as en7, with IPv4 manually set to 192.168.50.1/24. Ordinary IPv4

## Conclusion and remaining limits

The boot-reserved DMA receiver captures recognizable source audio, and the
normal firmware passes sustained and repeated-start acceptance over the fully
wired path. Clocked silence during HDMI renegotiation was distinguished from
absent samples and TCP/subscriber drops. A bridge reconnect recovered without
ending browser playback. These observations do not establish recovery from an
actual video resolution change or Xbox power cycle; those remain untested to
preserve the other chat's game session.

The fully wired result, versus Ethernet-KVM-to-Wi-Fi-Mac failures, points to
the common Mac/AP wireless path as a contributor. It does not isolate the
specific AP/radio mechanism or prove the KVM's own Wi-Fi never contributes.
Do not label the remaining wireless gaps a proven C790/I2S regression. Normal
browser IPv4 traffic still uses Wi-Fi while the Mac retains its existing
192.168.50.1 Ethernet configuration; connecting cables alone does not change
that routing. No Xbox files or network settings were changed.
The temporary browser tab, relay, packet captures and bounded test viewers
were stopped after validation. The normal 0c57c55 image remains installed;
changes are committed locally and have not been pushed.

## Mac network follow-up

On the user's subsequent explicit request, the Mac's USB Ethernet service was
changed persistently to DHCP while its previous Xbox subnet was retained in
a second macOS network service on the same physical en7 adapter:

- USB 10/100/1000 LAN: DHCP, acquired 192.168.1.220/24, router 192.168.1.1;
  remains first in network service order.
- Xbox Local: manual 192.168.50.1/24, no router; second in service order.
- Wi-Fi remains enabled as fallback. No Xbox or KVM settings were changed.

Both IPv4 addresses are simultaneously published on en7. Ordinary, unbound
HTTP to http://192.168.1.218/ now uses local 192.168.1.220, and route lookup
selects en7 for both the KVM and 192.168.50.0/24. Native browser audio was
active with a 43 ms playback buffer / zero backlog resets at the checkpoint;
packet headers verified its 960-byte PCM packets and ACKs on en7. A fresh
15-second standard observe_audio.py run, with no interface binding or relay,
captured 719,520 frames / 14.990 s PCM, RMS 0.183286 and 718,789 active frames.
The wired console was left open and audio muted after verification.

The Xbox project's documented current address is 192.168.1.254; it did not
answer ARP/ping/FTP over Ethernet, nor ping/FTP explicitly bound to the original
Wi-Fi path. The legacy 192.168.50.2 probe also failed before the change. Thus
the configuration and routes are preserved, but a live Xbox FTP session could
not be verified without leaving the running game. The project documents FTP
deployment while XBMC is running. The game session was not restarted.

Applied commands (sudo uses the Mac's existing administrative authorization):

```sh
sudo networksetup -createnetworkservice 'Xbox Local' 'USB 10/100/1000 LAN'
sudo networksetup -setmanual 'Xbox Local' 192.168.50.1 255.255.255.0 ''
sudo networksetup -setdhcp 'USB 10/100/1000 LAN'
```

To restore the previous configuration, first restore the primary service's
manual Xbox address, then remove only the added service:

```sh
sudo networksetup -setmanual 'USB 10/100/1000 LAN' 192.168.50.1 255.255.255.0 ''
sudo networksetup -removenetworkservice 'Xbox Local'
```

Use the wired KVM address .218 for normal browsing. The old .169 address names
the KVM's Wi-Fi interface even when the Mac itself is wired.

## Wi-Fi follow-up (router unchanged)

The user confirmed no router channel change was made. A fresh 30-second
capture explicitly bound to Mac Wi-Fi en0 (192.168.1.211), targeting KVM
Wi-Fi 192.168.1.169, returned HTTP 200 and ran 30.002803 seconds, but received
only 1,200,240 stereo frames (25.005 seconds PCM). It contained 1,146,008
active frames, RMS 0.015577, peak 0.125610. HTTP success therefore still does
not establish reliable wireless playback. This trial did not include a new
listener confirmation of recognizable source sound.

At the checkpoint, wdutil reported 5 GHz channel 132/80, RSSI -44 dBm,
noise -88 dBm, CCA 6%, 1200 Mbps TX rate, and AWDL disabled. Strong signal
and an inactive AWDL session did not eliminate the missing audio. Earlier
single-hop trials also lost audio with either endpoint using Wi-Fi; the
fully wired acceptance above remains the reliable baseline.

Evidence is in ignored observations/c790-wifi-2026-10-25/, including
unchanged-full-wifi-01.json, .curl.json, .headers, .pcm and .wav. The helper
was /tmp/kvm_wifi_hops.py. No router, firmware, or Xbox changes were made
for this trial. Channel 149 remains an untested hypothesis. Browser security
policy blocked access to the router administration page; the agent did not
attempt an alternate access path or bypass the warning.
